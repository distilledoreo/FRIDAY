## Native PC access — 0.18.0

FRIDAY also runs OpenCode directly as the PC user, with shell and X11 screenshot/input tools. Phone Settings → Computer access offers Ask every time, Ask before changes (default), and Full access, plus explicit shell allow/deny patterns and a desktop switch. Tasks, exact permissions, questions, cancellation, results and explicit screen preview live in FRIDAY on the phone. Chat PC tools require confirmation and are unavailable in incognito. Free cloud models can receive relevant PC outputs; local fallback is text-only, fixed to background slot 1, and uses the existing GPU/foreground gate. Existing sudo authorization applies; no password is stored or sudo policy changed. Changing access settings stops active work; later human follow-ups refresh the session rules. See [implementation and validation](../FRIDAY-COMPUTER.md).

The older isolated research agent described below remains available for explicit research jobs and existing schedules. Its restrictions describe that subsystem.

Native PC tasks use OpenCode Zen public free access, with a daily Artificial Analysis Intelligence Index ranking of currently listed zero-priced tool models. OpenRouter supplies score metadata only; it is not a native-task inference provider. Strong text-only models can drive reasoning/shell work; a separately ranked vision helper handles desktop work with the same phone permissions and free-only failover. Active turns keep their model identity/order; configuration updates wait for idle. See [model selection and verification](../FRIDAY-MODELS.md).

# FRIDAY isolated cloud agent

The PC gateway runs approved tasks through OpenCode 1.18.35 and the free-only OpenRouter broker. Android Activity lets the user review a plan, approve it, follow paged events and page previews, and cancel work. Models can propose tasks/actions but cannot approve them.

The execution container has four CPU threads, 8 GB RAM without extra swap, 256 processes, a read-only root, dropped capabilities, no GPU and `network=none`. Its only host mount is a task-specific Unix socket. Temporary work uses bounded RAM filesystems; containers and sockets are removed after completion/cancellation. No personal directories, host Docker socket, chat archive or provider credentials enter the container.

The host broker checks current catalog pricing and enforces free models with zero maximum token price, bounded requests and no paid/local fallback. Public HTTPS reads reject private, tailnet, metadata and other nonpublic addresses, pin validated DNS addresses, and revalidate redirects. Browsing is static page reading: Chromium previews have JavaScript and external resources disabled. Previews are authenticated PNG artifacts, not interactive logged-in browsing.

Approvals bind to exact payload fingerprints, cancellation revokes pending operations, and restart interrupts uncertain work without replay. Mail and limited primary-calendar executors are implemented behind a disabled production activation gate. Web submission, login, purchases and deletion have no executor. Proposed actions require exact review and separately enabled/verified provider setup.

Build with `python3 -m desktop.agent.build_image`; deploy the returned immutable image ID with `python3 -m desktop.agent.deploy --server-root /path/to/assistant-server --image sha256:... --restart`. Deployment backs up gateway source, checks for concurrent edits and idle state, then restarts only the API. It preserves the GPU maintenance pause and model configuration.

The host integration reads optional `outgoing.json` in the agent root. It enables execution only when its exact contents are `{"enabled":true,"phone_and_provider_verified":true}`. This is a trusted operator attestation, not an automatic test. Do not set it until real consent, phone review and provider execution/concurrency checks are completed and activation is explicitly authorized. No activation file was created for this delivery. Synthetic tests do not prove Microsoft Graph conditional updates on a real tenant. `GET /workspace/agent/outgoing/verification` reports the automatic checks (activation file, vault, send/calendar-capable accounts, idle executor) as capability booleans with no credential material, plus the remaining manual steps; it never changes the gate.

Operator MCP service connections live in optional `mcp.json` in the PC agent root (`{"servers":{"github":{"type":"local","command":[...],"environment":{...}}}}`, or `{"type":"remote","url":"https://...","headers":{}}` with per-server `enabled`). At most 10 servers with lowercase names; commands, environment, URLs, and headers are strictly bounded, and anything invalid is skipped without breaking the built-in computer server. Merged servers reload with the OpenCode config when idle, and their tool calls arrive as permission prompts in chat and FRIDAY like everything else: unknown tools ask by default in every mode except full access. Like `outgoing.json`, this file is a trusted operator attestation whose commands and credentials run on the user's own PC.
